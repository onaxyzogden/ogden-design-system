# Hybrid Design System — House Methodology

A shared methodology for designing and building web UI/UX across Ogden projects, synthesized from [[olos]] (OGDEN Atlas), [[milos]] (MIOS), and the principles/patterns cataloged at [DesignMotionHQ](https://designmotionhq.com).

**Core distinction this document holds onto: the *mechanism* is shared across every project; the *expression* is not.** OLOS's cool obsidian dashboard chrome and MIOS's soft-glass editorial warmth are not meant to converge into one palette — they're two skins over the same underlying methodology. A third project should start from the methodology below, then invent its own tokens, primitives, and motifs the way OLOS and MIOS each did.

---

## Layer 0 — Principles

Every project's own DESIGN.md should open with these, adapted from DesignMotionHQ's counter-thesis to schema-rendered AI UI:

1. **Intent-First Design** — before any pixel, name the actual users and their highest-stakes mistake. Don't default to generic CRUD assumptions. Then *model* those users: give every record a real reference to the actor it belongs to from the first schema, never a viewer-relative boolean like `isMine` or `ownedByCurrentUser`. A boolean answers "is this the current viewer's?" and silently loses "whose is it?", so any record created outside the current viewer's session belongs to nobody and can never be opened from the side that owns it. The bug surfaces late, as data that exists but is unreachable, and the fix is a migration rather than a patch.
2. **Hierarchy Over Defaults** — every screen gets a deliberate primary/secondary/tertiary ranking. Nothing is "equally weighted" by accident.
3. **System Consistency** — tokens live in one documented file. Off-system values are either promoted to intentional extensions or flagged as drift — never silently tolerated.
4. **State Completeness** — loading, empty, partial, error, success, and offline are designed upfront for every view that fetches or mutates data, not patched in later.
5. **Audit Against a Written Remit, Not Vibes** — before simplifying or auditing an existing screen, write down the role's actual responsibilities as a short enumerated list, then map every control on the screen against that list with an explicit verdict: keep it as is, fix a behavior bug, merge it into another control, defer it behind a disclosure, or cut it outright. A screen audited without a stated remit degenerates into taste — the loudest opinion in the room decides what's "clutter," and controls survive or die by who defends them rather than what they're for. The failure mode this catches: one decision offered through five separate controls because each was added in isolation to solve a real problem, with nobody ever re-deriving which responsibility the whole cluster actually served. Name the responsibilities first; the audit becomes mechanical once they exist.

## Layer 1 — Tokens

**Rule:** semantic tokens over literals, always, with a documented resolution/fallback chain.

- Every color, spacing, radius, shadow, and z-index value is a named token, never a hard-coded literal in component code.
- Spacing uses a numeric base-unit scale (e.g. 4px grid: `space-1` = 4px, `space-2` = 8px …), not t-shirt sizes — numeric scales say exactly how far apart two tokens are; t-shirt sizes don't.
- Where a token needs to express different values in different scopes (a tint, an accent), define an explicit fallback chain and document it, e.g.:
  ```
  scope-local-token → component-scope-token → domain-scope-token → global-default
  ```
  (This is OLOS's OKLCH elevation ladder feeding semantic aliases, and MIOS's `--motif-tint → --level-color → --pillar-accent → --primary` chain — same mechanism, different names.)
- A perceptually-uniform color space (OKLCH or similar) is worth adopting once a project needs a real elevation ladder (3+ surface levels that must read as evenly-spaced); skip it for simpler projects rather than importing complexity that isn't earned yet.
- Categorical data palettes (multi-series charts) are built in a perceptually-uniform space with lightness and chroma held constant and only hue stepped at even intervals — in naive RGB/HSL, some hues read as brighter than others at the "same" values, so one series looks more important by accident.
- Color is assigned by role, not by area. Neutrals carry their own scale — several surface steps, one or two border steps, and at least three text-emphasis tiers (primary, body, secondary/metadata) — and text hierarchy comes from those tiers before reaching for extra weights or hues. The brand/accent color is a full lightness ramp whose steps supply its hover, pressed, and disabled states, and it is reserved for interactive signifiers and status (primary action, active navigation, focus, selection) rather than spent on decorative card fills or icon tints. Fixed area ratios such as 60-30-10 suit simple persuasive compositions; dense operational surfaces sit far more neutral, with accent well under a tenth of the surface. Where a brand color fails contrast in its role, the brand yields — darken it, or pair it with an accessible companion shade — rather than the role accepting failed contrast.
- z-index gets its own small named scale (base/dropdown/sticky/overlay/modal/toast/tooltip/max), never raw integers in component code — and z-index only ranks siblings within the same stacking context, so isolate nested contexts deliberately rather than escalating numbers to compete across one.
- Type sizes come from a modular scale (a fixed ratio between steps), not arbitrary pixel values picked per-screen — the failure mode is a heading and a body size landing a few px apart and reading as a mistake rather than a choice. The ratio itself is a deliberate per-project choice (1.25, 1.333, 1.5, or the golden ratio's 1.618) held consistently across every step, not defaulted to or eyeballed step-by-step. Line-height and letter-spacing are set per step, not globally: large display steps take tighter leading and slightly negative tracking (type is spaced for body sizes and loosens as it scales up), body steps keep comfortable reading leading.
- Layout rests on a disciplined column grid; departures from it are reserved for deliberate emphasis, not habit.
- Visual grouping comes from a shared property — proximity via deliberately uneven whitespace, or shared alignment/color/enclosure — never from borders/dividers or uniform spacing everywhere.
- Gradient tokens keep hue rotation narrow (roughly within 60° of the wheel) and hold lightness direction consistent end-to-end; wide hue jumps or reversed lightness read as low-quality regardless of color space.
- Border-radius values form one proportional scale; a nested element's inner radius is derived from the outer radius minus the gap between them, never picked independently.
- A dark theme is not an inverted light theme: build it from a near-black (never pure-black) base with desaturated hues and an opacity-stepped text hierarchy, not remapped light-mode values. Depth in a dark theme comes from surfaces getting lighter as they elevate (canvas → card → popover/modal), because shadows barely register on dark ground; the lightness steps between dark surfaces need to be wider than their light-theme counterparts to stay distinguishable.
- Each surface declares its **register** — *persuasive* (marketing, landing, editorial, ceremony-adjacent storytelling) or *operational* (tools, dashboards, settings, data) — and the register sets the dials. Operational surfaces compress the type scale and spacing for density, hold strictly to the grid, keep accent scarce, and confine motion to functional feedback. Persuasive surfaces may use the full scale, generous whitespace, deliberate grid-breaks, varied section compositions (not one layout repeated down the page), and showpiece motion — provided that motion explains the product or the moment rather than decorating it. Most disagreements in practitioner advice (60-30-10, breaking the grid, 3D/scroll-driven motion) dissolve once the register is named. **Copy voice is a dial too.** An eyebrow, a slogan for a heading, or a badge repeated on every item is persuasive copy. On an operational surface it is a register leak, even when the type and spacing are already compact. An operational page names itself and states facts. **Comparison needs aligned rows.** When the job is to compare like items (people, rates, plans, records), give them a table or a list that lines the fields up. Cards make the eye read every card in turn. Say a caveat that applies to every row once, not on every row. **Density is held by width-aware tiers, not one breakpoint.** Keep values on one line where there is room. Let them wrap at word boundaries where there is less. Below the narrowest table that still fits, stack each row into labelled lines. Measure the tiers against the container the content sits in, not the window. **Warm is not persuasive.** A customer-facing flow (intake, booking, confirmation) may speak warmly, because the person is asking for help. It still does not sell, and it never shows the customer the operator's working state: review status, booking mode, scores or internal labels. Those are things the customer cannot act on. **Order is part of a comparison.** A list someone compares must come in an order they can read, usually time or price. The system's best pick may lead, marked once, and the rest follow that order. Ranking by an internal score reads as no order at all. **What the person can act on comes first.** On a narrow screen, real options (times, prices, the primary action) sit above the constraints and preferences that qualify them. **A workspace someone returns to lists their own items in the order they act on them.** First what waits on them, then what has a date, then what is in hand, then their drafts, then what is closed. Creation order is the system's order, not theirs. **One state, one word.** The badge, the tracker and the notifications say the same word for the same state. A raw internal status that reaches the person is the same leak as showing them the operator's working state. **Danger colour is for errors.** Something to approve is not an alarm. A count that names something to do should open it. **Accent repeated on every item is decoration.** One amber icon per task, or an accent fill on every note, is not scarce, so routine content sits on a neutral surface. Labels go in sentence case: capitals with wide tracking read as a stamp. **One action, one colour, everywhere it appears.** If Accept is green on one screen and amber on another, the person learns two actions, so the colour belongs to the action's role (primary), not to the screen. **One primary per screen.** When a screen opens on an item, a shortcut to that same item steps aside. In a list, each item's own button is secondary, because a filled button on every card is the same decoration as a repeated accent. **Headings inside a page sit below its h1**, item titles included. **Say the title once.** A one-item list under a heading that already names the item, or a disclosure labelled with the title again, says it twice, and a disclosure with nothing in it is hidden, not shown empty. **An empty state says what is true.** "You're done" needs something that was done. With nothing to do, it says so. **In a list, status colour says whose move it is.** Accent marks the rows that wait on the person; every other status sits on a neutral chip, and red stays for errors, so work in review is not red. When every row is amber, amber says nothing. **One move, one control.** A second way to do the same thing (a back button beside a list that is already on screen, or beside the toggle that opens it) is a duplicate to keep in step, not a convenience. **A filtered list that matches nothing says so and offers the way back** to the whole list. When the control that offered it disappears, focus goes to where the person will look next, not to the page. **A label is for the person; its value is the system's.** A filter can read in sentence case while keeping the system's status string as its value, so the words change and the logic does not. **A fact is not a state.** A booking mode, a job's duration or a summary of the work sits on a neutral surface in plain text; a chip or an accent tint says there is something to do. **A status chip keeps one rule on every screen it appears**: the detail beside a list colours it as the list does, and a status that waits on someone else (an offer out to a contractor) is neutral wherever it sits. **A fact every item shares is said once, above them.** The same buffer or fit line on each of three time slots pushes apart the thing that differs. **Where the toast has no undo, a recoverable removal asks first.** The undo window in Layer 3 is still the aim; a confirmation is the fallback until the toast can carry one, not a reason to stop there. **A greeting is a slogan.** Home names itself too; "Good morning!" says nothing about the page. **A heading names the scope it shows.** A view that can show another day says which day it is ("Today" only on today, otherwise the date), because misreading the scope is the worst case on a schedule. **Totals count the same set the list shows.** Two totals for one day that count different things read as a contradiction. **An illustration says only what it knows.** A schematic map draws one mark per real item and no route it cannot know; when it cannot be accurate it shows the count, not a picture of precision. **An end screen says what is still waiting.** A queue that was skipped through is not "all caught up"; it says how many are left and where they wait, and the all-clear shows only when nothing is. **Breaking what someone else holds asks first.** An action whose effect lands on another person and cannot be undone, such as withdrawing or replacing a link they hold, asks first even when it is a replacement rather than a removal; when nothing would break, it acts in one step. **A link that no longer works is not offered.** Once a link is withdrawn or expired, controls that copy or preview it are hidden rather than left to fail, the heading names the state instead of the wait it ended, and replacing the link becomes the one move.

## Layer 2 — Motifs & Primitives

**Rule:** one canonical primitive per concern. When a second one appears, the old one becomes a deprecated forwarding wrapper — it is not deleted, and it is not left to drift independently.

- Each project names its own small vocabulary of reusable visual "moves" (3–6 motifs is plenty). OLOS's is a single surface primitive (`BentoBox`); MIOS's is five named effects (halo, ghost-text, soft-glass, shimmer-border, editorial serif). A new project should do the same exercise from scratch rather than importing either list.
- Every motif/primitive documents:
  - What problem it solves (what was being duplicated before it existed)
  - Its fallback/tint contract, if it takes a scoped color
  - When **not** to use it (one-off brand moments, throwaway prototypes, non-visual state signaling)
- Composition rules matter as much as the motif itself: don't stack two of the same animated effect on nested elements, gate every animation under `prefers-reduced-motion`, and make sure light/dark variants are both defined whenever a scope overrides a tint. Anything that moves continuously or loops for more than a few seconds (a marquee, a rotating shimmer stroke, an ambient gradient) also carries a visible pause control — reduced-motion gating alone doesn't serve the user who is merely distracted by it.
- Icons are a primitive too: pick one icon set and one sizing scale (e.g. 16/20/24/32/48px for inline/default/nav/feature/hero contexts) and stop there — mixed icon styles or ad hoc sizes read the same way mismatched primitives do. Regardless of the icon's visual size, its tappable/clickable area should never drop below ~44×44px. Icons in the set additionally share stroke weight and one fill-or-outline choice, with rounded glyphs given slight optical upsizing to read as the same size as square ones. An icon sitting inline with a text label takes its box size from the label's line-height, not its font-size, so the pair centers optically.
- Motion timing is part of the primitive's contract, not an afterthought: pair easing to direction (ease-out entering, ease-in leaving, ease-in-out for moves/resizes) and scale duration to the weight of what's moving (roughly 100-200ms for hover/toggle-scale feedback up to 400-500ms for page-level transitions) — document both alongside the motif the same way its tint/fallback chain is documented. When two signals represent one state change (an icon rotation and a panel expansion), they run on the identical timing curve — desync between them reads as broken, not as two effects.
- Motion must earn its implementation and performance cost: it signals a state change, directs attention to what matters, or explains a spatial relationship — otherwise it's cut, however good it looked in a prototype. Spatial motion preserves continuity: an element expanding into a view grows from where it sat, and content moved by a swipe travels along the swipe's direction rather than cutting or sliding in from somewhere unrelated.
- Overlays (menus, dropdowns, popovers, tooltips) detect available viewport space and reposition or flip themselves so they never render clipped off-screen.
- No interaction that matters may depend on hover or gesture alone: every hover-revealed action and every swipe/drag gesture needs a discoverable, tap/keyboard-reachable equivalent, detected via capability query rather than inferred from device type.
- Interactive-state cues (an inline-edit affordance, a hover effect) reveal themselves through tint, icon, or shadow — never by resizing or shifting the element's layout footprint, which would displace neighboring content.
- A pattern is substituted for a different one when the breakpoint changes the interaction model (e.g. tabs → bottom sheet on mobile), not just visually shrunk. On handheld breakpoints, high-frequency controls move into thumb reach at the bottom of the viewport rather than staying where the desktop layout put them.
- A tooltip holds one short phrase; once an explanation needs more than that, it's replaced by a popover or inline-help pattern instead. Tooltips open only after a deliberate hover-intent delay and close immediately on leave, so sweeping the pointer across a dense toolbar doesn't spray them.
- Progressive disclosure is the default for secondary capability: a surface shows the actions its current state calls for, not every action it supports. Secondary row/card actions collapse into an overflow menu beside one visible primary; selection-dependent actions (bulk delete, export, tag) appear in a contextual bar only once something is selected; advanced options sit behind an accordion or popover.
- Behavior is as consistent as tokens: one action uses one control style everywhere, and one control style never triggers different kinds of outcome on different screens. Users tolerate plain visuals far better than inconsistent interaction logic.
- Frequently repeated actions get keyboard shortcuts, and each shortcut is surfaced where its action lives (a hint inside the control, beside the menu item) rather than only in documentation.
- Long collections prefer explicit continuation — a load-more control or pagination — over unbounded infinite scroll, which strands footer content and makes position impossible to hold or return to; infinite scroll is reserved for feeds where position genuinely doesn't matter.
- An interactive preview state (hover, drag-to-rate) renders visibly distinct from the committed state and reverts cleanly if the interaction is abandoned before commit.

## Layer 2.5 — Pattern Reference

**Rule:** don't re-enumerate the tactical pattern library inside the house methodology — cite it, then document which patterns a project drew from.

[DesignMotionHQ's `/patterns` catalogue](https://designmotionhq.com/patterns) (76 named patterns across Content, Feedback, Forms, Interaction, Motion, Navigation, and Visual — see the index below) is the tactical menu that Layers 2 and 3 pull concrete choices from. This methodology is a meta-layer above that catalogue, not a competitor to it — it governs *how* a project picks and governs patterns, not *which* date-picker or modal-hierarchy to use.

- When a project needs a concrete pattern (a form field state, a data table, a command palette, an easing curve), the DesignMotionHQ catalogue is the first place to look before inventing one.
- Every pattern adopted from the catalogue gets recorded the same way a motif or primitive does (Layer 2): what it's used for, its token/tint contract if any, and when not to use it. A project's DESIGN.md should keep a short "patterns in use" list naming which catalogue entries it has adopted, so the choice is documented rather than ad hoc.
- Two catalogue categories map directly onto layers already defined here rather than needing their own list:
  - **Feedback patterns** (toast, skeleton loading, optimistic UI, undo UX, error states, Doherty threshold) *are* the frictionless-feedback half of Layer 3's ceremony/frictionless split.
  - **Visual patterns** (design tokens, shadow elevation, border radius, dark mode, depth layers) *are* Layer 1/2 mechanism, expressed as named patterns rather than raw tokens.
- Categories with no house-level equivalent yet (most of Forms, most of Interaction, Navigation specifics, Motion specifics beyond reduced-motion gating) are intentionally left to per-project judgment, sourced from the catalogue as needed — the house methodology doesn't take a position on, say, OTP input design or command-palette behavior.

## Layer 3 — Thresholds & Feedback

**Rule: ceremony is earned, not default.**

A boundary in the UI gets a deliberate ritual pause (a la MIOS's Ceremony Gate) only when at least one of these is true:
- The action is **irreversible** or high-stakes
- The boundary is **identity-bearing** — entering it is meant to change the user's mental state, not just their route (e.g., a covenant/intention moment), not a generic "next screen"
- The user is **returning after meaningful absence** and needs re-grounding, not just a reload

The ceremony need not be a dialog: for an irreversible action on touch surfaces, a deliberate physical gesture (a full-width slide-to-confirm) is itself the pause — accidental taps can't complete it — provided a keyboard/assistive equivalent exists per Layer 2's parity rule.

Everything else gets DesignMotionHQ-style frictionless feedback instead:
- Inline validation timed to avoid interrupting typing. **Never disable a submit control to express that a form is incomplete.** Three things break at once when you do: the control drops out of tab order, so keyboard users cannot reach it; it is silent to screen readers, which announce it as unavailable without saying what is missing; and disabled elements fire no pointer events, so the tooltip explaining the block never opens for anyone. The greyed label usually fails contrast on top of that, which is how a control meant to *inform* people ends up being the least legible thing on the screen.
  The replacement: the control stays enabled, always clicks, and validates on click. On failure, mark the specific blocking field, render the reason beside that field — inline, never a tooltip — and move keyboard focus to it. Do this **per field**, so each blocking condition carries its own message and its own focus target; one global "the form is invalid" flag cannot tell anyone which thing to fix. Two caveats worth stating: focus only lands reliably when the target is already rendered at click time, so this pattern fits fields that are visible rather than ones that appear as a result of the click; and a control that is read-only because the record belongs to someone else is not a blocked action at all — render it as text or `readOnly`, not `disabled`.
- Toast notifications for non-blocking status
- Every control that starts asynchronous work acknowledges the press immediately with a pending state on the control itself (inline spinner, pending label) that also guards against a duplicate submission — silence after a click reads as failure and invites a second click. The guard ignores repeat presses while pending (and marks the control busy for assistive tech); it does not set `disabled`, for the same reasons the validation rule above gives.
- Skeleton/loading states that communicate progress, not just delay
- Empty states that guide the next action, not just say "nothing here"
- Completion guides the next action too: a flow that creates something (a workspace, a project, a record) offers the next logical step — with an explicit skip — rather than dead-ending at "Saved". Flows are designed as connected sequences, not isolated screens.
- Machine-generated output is a feedback surface with its own obligations: stream it as it's produced rather than blocking on the whole; make multi-step work visible as its steps run; let the user see, edit, and remove whatever the system retains about them; and mark which claims are grounded in a cited source versus unverified — never present the two identically.
- Optimistic UI is reserved for low-stakes, reversible actions; irreversible or financial actions always wait for authoritative server confirmation before declaring success, regardless of client-side pre-validation.
- A destructive-but-recoverable action (delete, archive, remove) defaults to an undo window — a toast holding an undo affordance for several seconds — rather than a confirmation dialog; a confirmation dialog is a ceremony gate and belongs only to actions that are genuinely irreversible, per this layer's own threshold rule.
- Autosave commits on a debounce tied to natural pauses in input, never on every keystroke, and the interface always makes visible whether current content is local-only, pending, or confirmed-saved.
- Feedback surface and prominence scale with severity and how much progress it blocks: badges or inline text for passive information, toasts for non-blocking status, banners for warnings, and modals reserved for responses that are genuinely required. The same discipline picks a loading indicator — skeleton when the layout is known, spinner for brief unknown delays, progress bar only when real percentage data exists.
- Flow-level UX answers to psychology, not just per-screen state: concentrate design effort on a flow's peak moment and its ending, since they're remembered disproportionately (peak-end effect); place a sequence's most critical content or call-to-action at its start or end rather than the middle (serial-position effect); use partial-completion cues to motivate return-and-finish only when the underlying goal is genuinely the user's, never manufactured to inflate engagement (Zeigarnik effect).
- Interface copy — labels, errors, empty states — is a feedback surface in its own right: write it in plain, benefit-oriented language, not system-centric jargon.
- In-progress and navigable state (multi-step form input, pagination/filter/sort state) survives reload, the back button, and sharing a link — persist it rather than letting navigation silently discard it.

**Why the split matters:** ceremony that fires on every screen stops being ceremony — it becomes friction, which is precisely the "AI-generated UI wastes the user's time" failure DesignMotionHQ is naming. Scarcity is what makes a ritual moment register (the same mechanism as the Von Restorff effect: isolated things get noticed; ubiquitous things don't).

## Layer 4 — Governance

- **ADR trail.** Every token-level or primitive-level decision gets a dated architectural decision record — not just a comment in code. Future sessions (human or agent) should be able to answer "why is it this way" without archaeology.
- **Anti-pattern list.** Maintain an explicit "do NOT use" list alongside the positive guidance — generic/undifferentiated design, AI purple/pink gradients, emojis as icons, missing `cursor: pointer`, invisible focus states, disabled submit controls standing in for validation, instant (non-transitioned) state changes, encoding status/severity/destructive intent through color alone (pair it with an icon, label, or shape, and reserve the danger/red channel exclusively for destructive or irreversible actions so it stays trustworthy), distorting a chart's axis scale in a way that overstates the magnitude of a change, decorative charts that drop axes, values, or legends or whose bar count doesn't map to real periods, engagement mechanics that work through guilt or loss rather than genuine utility (streak-loss threats, lives/penalty systems, nagging re-engagement notifications, rivalry leaderboards), and the generated-without-review "tells": the same summary-metric cards repeated across every sub-page, placeholder cards that carry no data or action, and table rows crowded with a full set of action buttons.
- **Pre-delivery checklist.** Before shipping any UI work, verify contrast ratios, focus visibility, reduced-motion handling (and a pause control on any continuous motion), responsive breakpoints, that new surfaces compose the canonical primitive rather than rolling a new one, and that the surface holds up under worst-case content rather than ideal placeholder data — overlong strings truncate or wrap deliberately, missing images degrade cleanly, and controls overlaid on user imagery keep their contrast.
- **"Test harness" and "legitimately useful chrome" are not reliably distinguishable up front.** Controls that exist to make a thing testable — role switchers, identity pickers, seeded-data resets, simulated-clock controls — are easy to dismiss as scaffolding and strip out as not-product. Sometimes that is right. But a prototype whose whole job is to be evaluated by other people may be untestable without them, and stripping them can cost more than it removes. Decide it late, against someone actually trying to use the thing, rather than early on principle; and if such a control is cut and then needed back, record that it was cut and why, so the next round does not relitigate it from scratch.
- **Flows before fidelity.** A flow is mapped at low fidelity — entry points, skips, modals, hidden and error states — before any of its screens goes to high fidelity; structural gaps are cheap to find in a sketch and expensive in polished pixels.
- **Repair order for confusing UI.** When a surface reads as confusing, fix in this order: hierarchy (is one thing clearly primary?), then alignment to the grid, then disclosure (how many choices are visible at once), and only then visual styling. Restyling a surface whose hierarchy is broken just produces a better-looking confusing surface.
- **Review through working prototypes.** Design decisions are reviewed through an interactive prototype shown in realistic context — states, transitions, and feedback included — not static or stylized showcase renders (skewed, exploded, collaged), which flatter a design while hiding broken flows. Showcase framing is for publicity, never for a decision review.
- **Drift gets flagged, not tolerated.** An off-system value is either promoted to a documented, intentional extension of the token set, or corrected — it never just sits there unaddressed.
- **A derived value must have a writer.** A routing/bucketing function (status derivation, feature-flag resolution, any read-side function that classifies state) is verified two ways, not one: that every branch produces a sensible result, and that every branch is actually reachable from something the write side produces. A branch that recognizes a value nothing ever writes is not harmless coverage — it reads as tested and correct while doing nothing, hides that the write side was never built, and misdirects debugging toward the router when the bug is upstream. When found, the fix is binary: write the value somewhere real, or delete the branch — never leave it recognized-but-dead.
- **Naming conventions are written down, not inferred.** Token names, CSS class conventions (BEM or otherwise), and component prop naming should be documented once per project rather than reverse-engineered by whoever joins next — this is what makes the anti-pattern list and pre-delivery checklist actually checkable by someone new.

## What Stays Project-Local (not house style)

Concrete example from the two source projects, to make the mechanism/expression distinction unambiguous:

**OLOS-specific (do not inherit as-is):** no blue as primary action color; no border-radius greater than 6px; the two-gold brand/active split; the "High-Tech Earth" cool-obsidian chrome palette; Fira Code + Fira Sans as the specific typefaces.

**MIOS-specific (do not inherit as-is):** the five specific motifs (halo, ghost-text, soft-glass, shimmer-border, editorial serif); ceremony gate copy and ayat content; the editorial-serif treatment itself.

A new project inherits the *practice* — pick your own constraints, name your own motifs, choose your own type pair, document all of it — not the specific values above.

**Taste calls the house deliberately leaves open** (each is a legitimate per-project choice, documented in that project's DESIGN.md, not a house rule): one typeface vs. a display/body pair; brand-hue tinting of neutrals; pure-white vs. off-white canvas; border-led vs. shadow-led separation in light themes; corner smoothing (squircles); glass/blur surfaces; celebration effects on completion; and specific layout archetypes (bento grids, visual mega-menus, tabbed feature showcases).
